## 오늘 한 일

### 1. Supabase 무료 플랜 egress 초과 대응 (핵심)

경고 메일 수신. 5.5GB 초과, 유예 9/8 까지. 8기가 8/10~9/4 라 **기수 중간에 앱이 멈출 위험**이 있었다.

**원인**: 데이터 양이 아니라 같은 응답을 반복해 다시 받는 폴링. 두 군데.

- `globalPeerTick` (20초) : `document.hidden` 가드가 없어 **백그라운드 탭도 계속 폴링**.
  매 틱 3일치를 `force: true` 로 받아 캐시를 아예 안 탔다.
- `refreshRemoteStateAndCommunity` (15초) : 내 app_state(85KB) + 멤버 요약(20KB) + 커뮤니티 글(47KB).
  커뮤니티 글은 항상 `force: true`.

실측: 멤버 1명당 탭 열어둔 상태로 **시간당 약 60MB**, 백그라운드로도 25MB.

**고친 것** (커밋 `272cde9`, 7기·8기 동시):
- `globalPeerTick` 에 `document.hidden` 가드
- 주기 20초 → 60초
- 매 틱 3일치 → 오늘 1일치 (날짜 바뀐 직후 1회만 앞뒤 확인, `window.__peerLastDay`)
- `PEER_CACHE_MS`(60초) 신설. 피어 보드·커뮤니티 글 캐시 수명만 늘림
- `refreshRemoteStateAndCommunity` 의 `loadCommunityPosts` 를 `{force:true}` → `{force}`

**일부러 안 고친 것 ★★**

내 app_state 동기화 주기(`COMMUNITY_REFRESH_MS` 15초)는 그대로 뒀다.
트래픽으로는 이게 제일 크지만, `upsert_member_app_state` 가 `app_state = excluded.app_state`
**통째 덮어쓰기**라 주기를 늘리면 다른 기기에서 쓴 내용을 모른 채 저장해 덮어쓸 수 있다.

> 폰에서 문장 작성 → 노트북 탭은 계속 보이는 상태라 remote 를 안 받음 → 노트북이 저장 → 폰 문장 소실

버디가 "절대 데이터 날아가면 안 된다" 고 했고, 15초 폴링이 그 창을 좁게 유지하는 안전장치다.
**`COMMUNITY_REFRESH_MS`(내 상태 동기화)와 `PEER_CACHE_MS`(남의 데이터 캐시)를 다시 합치지 말 것.**

검증 통과: script 블록 3개 파싱 OK · em dash 검사 0 · 가비 0 (7th/8th 양쪽)

예상 효과: 시간당 60MB → 25MB, 백그라운드 0. 원안(4MB)보다 작은 건 app_state 를 안 건드려서다.
