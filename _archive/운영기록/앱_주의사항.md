## 배포

### 연속 푸시 금지 ★

GitHub Pages 는 Actions 로 배포되는데, **새 푸시가 진행 중인 빌드를 취소한다.**
원인을 찾겠다고 짧은 간격으로 연달아 푸시하면 서로를 계속 죽여서
"아무것도 반영이 안 되는" 상태가 된다. (2026-08-07 에 13:47 / 13:51 / 13:53 전부 cancelled)

**규칙: 푸시 후 빌드가 끝날 때까지 다음 푸시를 하지 않는다.**
반영이 안 될 때 제일 먼저 의심할 것은 코드가 아니라 빌드 상태다.

### 커밋 전 검증 3종

## 코드에서 조심할 것

### 함수 반환 필드를 바꿀 땐 소비처를 전부 grep

`computeVerifyScore()` 의 `.score` 를 `.days` 로 바꿨더니
체크보드가 `undefined >= 18` 을 평가하게 됐고, 이건 **에러 없이 조용히 false** 가 된다.
결과: 본인 이름에 완주 🏅 가 절대 안 붙는 상태로 이틀을 갔다.

→ 지금은 `.score` / `.scoreText` 를 레거시 별칭으로 남겨뒀다.
→ 교훈: JS 에서 오타난 속성 접근은 터지지 않는다. 이름을 바꾸면 반드시 전수 grep.

### 지각 판정의 유일한 정답은 `dayStatus(d)`

`state.verified_late` 는 **읽는 곳만 있고 쓰는 곳이 없는 레거시 키**다.
이걸 기준으로 계산하면 항상 0 이 나와서 아무 일도 안 일어난다.
지각은 `dayStatus(d) === 'done-late'` 로만 판정한다.

### 완주 판정 경로가 본인/남이 다르다

- 남의 행: `m.progress` (서버 RPC 가 세어준 인증 일수)
- 본인 행: `computeVerifyScore().days` (로컬 계산)

둘 중 하나만 고치면 절반만 맞는다. 항상 같이 확인.

### 서비스워커 캐시

`activate` 에서 **자기 prefix 로 시작하는 캐시만** 지운다.

```js
keys.filter(k => k.startsWith('youbuddy-7th-') && k !== CACHE_NAME)
```

전부 지우게 두면 7기와 8기가 서로의 캐시를 죽인다.
(멤버 데이터는 안전하다. Cache API 에는 정적 GET 만 들어간다.)

### 팝업을 추가할 때 체크리스트

1. `anyPopupOpen()` 에 등록
2. 본 상태를 `state` 에 저장하고 `PERSISTED_STATE_KEYS` 에 추가
3. 렌더 훅에서 `data-attr` 로 중복 생성 방지 + else 브랜치에서 remove
4. 닫기 경로 전부 처리 (X · 배경 클릭 · 나중에 · CTA)
5. **트리거를 실제로 호출하는지 확인.** 컴포넌트만 만들고 부르는 데가 없어서
   Week 4 다시보기 팝업이 안 뜬 적이 있다.

### 운영자 전용 버튼이 실데이터를 오염시키지 않게

`__bingoOperatorSkipFinal` 이 `bingo_done['4']` 를 써버려서
운영자 계정이 "파이널 완료"로 잡혔다. 완료 판정은 `final_test.at` 으로 봐야 한다.

## 발표 피드백 리포트 앱에 올리는 절차

1. 편집본에서 `.bar` · `.hint` · `<script>` 제거, `contenteditable="false"`
2. `<meta name="robots" content="noindex,nofollow,noarchive">` 추가
3. 우상단 고정 `📄 PDF로 저장` 버튼 삽입
4. `7th/report-{sha앞20자}.html` 로 저장
5. `MEMBER_REPORTS` 에 **한글 이름과 영문 닉네임 두 키 모두** 등록
   (`MEMBER_DIRECTORY` 의 `name` 이 영문인 멤버가 있어서 하나만 넣으면 안 잡힌다)
6. 두 키 중 하나에만 `label` 을 넣는다 (운영자 목록에 두 번 뜨는 것 방지)
7. 두 회차 합본이면 `weekLabel: 'Week 3~4'`

운영자는 프리미엄 탭 카드에서 `__openReportList()` 로 전체 목록을 본다.
리포트가 없는 멤버에게는 같은 자리에 `/sample-report.html` 카드가 뜬다.

## 데이터베이스 (SQL 함수) · 2026-08-11 사고

**기수별 시작일이 SQL 함수 안에 하드코딩돼 있다. 새 기수를 열면 반드시 추가한다.**

8기 Day 1 에 인증자 26명 전원이 지각으로 찍혔다. 원인은 `get_cohort_member_summaries` 의
`cohort_start` 에 8기가 없어서 `else` 로 빠졌고, 기본값이 7기 시작일(7/13)이었던 것.
Day 1 마감이 7/14 로 계산되니 8/10 인증은 전부 한 달 늦은 셈이 됐다.

- **함수가 여러 개다.** `get_cohort_member_summaries` 와 `get_cohort_awards_late_days` 가
  각자 자기 `cohort_start` 를 들고 있다. 하나만 고치면 나머지가 조용히 틀린 값을 낸다.
  (실제로 awards 쪽은 8기가 있었고 summaries 만 없어서, 같은 데이터에 지각 0건 vs 26건이 나왔다.)
- **RPC 가 `p_cohort` 를 받는다고 해서 기수 대응이 끝난 게 아니다.** 함수 본문을 열어볼 것.
- **추가한 뒤 실제로 조회해서 검증한다.** 새 기수 Day 1 인증자의 지각이 0건이어야 정상.
  전원 지각이면 시작일이 틀린 것이다.
- 기수 날짜가 박힌 파일 전수 확인: `grep -l "when '[0-9]기'" supabase_migration_*.sql`

## 인프라 · 비용

상세는 노션 `🐤 유비챌 운영 → 🧱 인프라 · 비용 기준 (Supabase)`.

- **과금은 프로젝트가 아니라 조직 단위.** 한 조직에 프로젝트가 둘이면 활동량과 무관하게 $10 이 더 붙는다.
- **무료 플랜 프로젝트는 7일간 활동이 없으면 자동 일시정지된다.** 정지되면 멤버가 사이트에 들어와도
  아무것도 안 보인다. 평생소장 약속이 깨지는 지점이라, 무료로 갈 거면 매일 Supabase 를 건드리는
  스케줄이 살아 있어야 한다. Pro 는 자동 정지가 없다.
- **egress 가 터지는 건 데이터가 많아서가 아니라 같은 응답을 반복해서 받기 때문이다.**
  (백그라운드 탭 폴링, 캐시 무시 force fetch). 2026-08-09 수정으로 하루 300~470MB → 70MB.
- 남은 최대 항목은 15초마다 개인 기록 전체(85KB)를 통째로 주고받는 부분. 2.0 에서 델타 동기화로.
